02 목표

명령 하나로 두 로봇이 한 바퀴, 화면에 3D 메시

  • 로봇 Pinky Pro 2대 · 카메라 RealSense D455 2대
  • 표식 판: A1 출력 → 594 × 594 mm, AprilTag 85 mm × 16
  • 물체: 바닥 지름 0.28 m 원 안, 높이 0.20 m 이하
  • 두 높이 각 24시점 → 48시점 융합

03 계획서 작성

계획서에서 코드보다 먼저 정한 것

  • 역할로봇: 원자료 전송 · 주행 명령 실행
    스캔 PC: 영상 처리 · 자세 · 주행 판단 · 융합
  • 영상연속 스트림 대신 요청할 때만 스냅샷
    연속 스트림 로봇당 초당 약 40 MB ↔ 스냅샷 시점당 약 4.3 MB(압축 약 1.6 MB)
  • 카메라 자세와 로봇 주행3D 융합은 각 사진의 바닥 표식으로 자세 결정
    주행은 표식을 기준으로 바퀴의 이동·회전량 반영
  • 접점 고정좌표계 · 스냅샷 형식 · TCP 메시지 · 데이터셋 · 설정 파일 하나
  • 출발점 · 공개 예제pinky_pro · command_driver · librealsense · Open3D · OpenCV

05 개발 절차 · SDD · TDD란

명세로 '무엇'을 정하고, 테스트로 '됐는지'를 확인한다

SDD

Spec-Driven Development · 명세 주도 개발

코드보다 명세를 먼저 쓰고,
명세를 기준으로 구현하고 검증한다

  • 명세에 담는 것하는 일 · 입력과 출력 · 동작 · 완료 조건
  • 얻는 것모듈 사이 약속이 먼저 정해져, 나눠 만들어도 맞물림

TDD

Test-Driven Development · 테스트 주도 개발

실패하는 테스트를 먼저 쓰고,
통과할 만큼 구현한 뒤 코드를 정리한다

Red실패하는 테스트
Green통과하는 구현
Refactor테스트를 지키며 정리
  • 얻는 것고칠 때마다 전체를 다시 확인, 고친 곳 밖이 깨지면 바로 앎
이 프로젝트에서

명세의 '완료 조건'이 TDD의 첫 테스트가 됨 → 현장에서 고칠 시간이 없으니, 실물 없이 미리 검증

TDD 순서

  1. 명세의 완료 테스트를 코드로
  2. 실행해 실패 확인
  3. 구현해 pytest 통과
  4. 할 일 목록에 체크, 다음 모듈로

규칙

  • 모듈 사이 약속은 계획서가 기준
  • 통과 기준 수치는 계획서 값 그대로
  • 빠른 시험은 수시로, 오래 걸리는 통합 시험은 따로

현장 데이터도 테스트로

설계 변경도 테스트 먼저

옛 코드에서 실패 확인 → 코드 수정 → 명세 · 테스트 반영
